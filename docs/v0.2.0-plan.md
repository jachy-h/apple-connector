# Apple Connector v0.2.0 开发计划

状态：实现进行中；P0/P1 基础设施、P4 管理切片与 P5 本地候选验证已完成，原生门禁与分发验收仍阻塞。
更新日期：2026-09-06
进度记录：[v0.2.0-progress.md](./v0.2.0-progress.md)

## 1. 目标与版本衔接

将已有本地连接器原型推进到可验证的发布候选：先解决原生写入超时和恢复证据缺口，再补齐受控修改、Calendar 写入、安装权限验证与分发。

本计划承接 [v0.1.1-plan.md](./v0.1.1-plan.md) 的未完成范围；v0.1.0 原型基线与 v0.1.1 实验记录保留为历史证据。制定计划不代表这些版本已验收，也不代表当前 package 版本已升级。

沿用 TypeScript、Node.js、固定 JXA 脚本、本地服务与 MCP 架构。所有写入继续经过范围授权、不可变计划、执行前复查、持久化意图、原生执行及回读核验。无法可靠判定对象是否受支持时拒绝写入；结果未知时禁止盲目重试。

## 2. 当前基线与待解决问题

- 已具备后台服务、CLI、MCP、客户端授权、审批、审计、日志保留与四个基础管理页面。
- 三类数据源已有受限读取；Reminders/Notes 受限创建已接入，并有专用容器历史原生验证记录。
- 2026-09-06 仓库复核：`npm run check` 在允许本地 socket/loopback 监听的环境下通过，包含 53 项核心测试和 17 个固定 JXA 脚本语法检查；不代表真实 Apple 写入复测通过。
- Reminders 更新/完成探针运行超时，阻塞阶段尚未定位；旧基础 CRUD 探针也有超时记录，需同时复核现有创建链路的可靠性。
- 恢复脚本只匹配原始标题，而更新探针会追加 ` updated`。历史 `removed: false` 只能证明当时未匹配原始标题，不能排除已改名对象或同步延迟后的残留。
- Calendar 的 Apple Events 稳定标识读取失败；历史 EventKit 授权状态与目标日历可见性不一致。
- 现有接口调查未得到足够可靠的共享/重复状态判定方案。此问题可能限制可支持范围，不能以可写性、账户类型或字段缺失代替判定。
- README 与原生验证记录包含“未接入 writer”“管理界面尚未实现”等过时描述，需按代码和实际证据统一。

## 3. 开发方案

### P0：修复探针对账与恢复

涉及 `scripts/jxa/diagnostics/reminders-update-crud.js`、`reminders-delete-m1-probe.js`、`src/jxa/protocol.ts`、诊断调用端与测试。

1. 写入前由调用端生成并持久化探针 UUID、明确容器 ID、开始时间和状态。取得稳定提醒 ID 后立即保存；诊断记录不保存用户正文、token 或原始原生错误。
2. 优先按“容器 ID + 稳定提醒 ID”恢复。尚未取得 ID 时，仅在原授权容器内精确匹配该 UUID 对应的原始标题和已知更新标题，合并结果并按稳定 ID 去重；多个候选拒绝，不能按前缀批量删除。
3. 将发现、核验、清理分开。删除前重新确认目标仍是同一探针；删除后按稳定 ID 回读，只有核验通过才能报告清理成功。
4. 区分 `not_found`、`removed_verified`、`ambiguous`、`outcome_unknown` 等诊断结果。单次未找到不能等同于原操作未执行或永久无残留；允许有界只读复查，不自动重放写入。
5. 对历史已持有 UUID/稳定 ID 的未决探针逐项对账。无法取得可靠定位依据的历史对象保留为待人工核验，不扩大搜索或删除范围。

验收：覆盖原始标题、更新后标题、重复匹配、跨清单、缺失对象、删除后仍可见、删除超时及延迟可见；恢复不会处理其他对象。先补齐恢复能力，再运行新的写入探针。

### P1：定位 Reminders 超时并验证原生链路

涉及 `src/jxa/runner.ts`、固定诊断脚本、`tests/jxa.test.ts` 与 `tests/native/diagnostics.test.ts`。

1. 将单个长脚本拆成有明确边界的诊断步骤：容器解析、创建、取得 ID、范围回读、字段修改、完成、核验、清理。调用端在每一步前后记录阶段枚举、耗时和结果。
2. 若单步内部仍阻塞，增加严格 schema、大小限制和脱敏的阶段事件通道；不得将任意 stderr 转为日志，不得把阶段事件误当最终成功回执。
3. 为每步和整次实验设置时间/次数上限；区分 Apple Events 调用阻塞、写后同步可见性滞后、权限拒绝与协议错误。只读核验可有界退避，写入不自动重试；不将单纯延长 60 秒超时作为修复。
4. 审核异常映射：发生写入后响应丢失、JSON/身份校验失败、进程异常或回读失败时，仍须保留未知结果语义，不能报告确定未写入。
5. 在指定 `Agents` 清单中分开验证创建、标题/备注、date-only、带时区日期、完成和清理；每次实验使用独立 UUID，记录运行环境与恢复结论。

验收：可定位每次失败的最后已知阶段；每个支持动作至少有三次独立、可核验的真实运行记录；故障注入覆盖写后响应丢失和未知结果不重放。若现有创建不能稳定通过，应收紧对应能力声明。

### P2：建立支持矩阵与 Calendar 定位方案

1. 为每个 provider/动作记录支持条件、拒绝条件、公开接口依据和实测证据，区分“接口存在”“内存测试”“真实访问”“最终安装验证”。
2. Reminders 优先验证 EventKit 的真实对象访问和重复规则识别；单独核验清单共享状态是否可可靠取得。脚本字典缺少 recurrence 不等于普通提醒。
3. Calendar 分离容器定位与事件定位实验，验证稳定标识在改名、重启、同步和最终安装路径下的行为；记录标识失效、歧义与重新绑定方式。不得把名称或事件标题当作稳定写入身份。
4. 诊断 EventKit 授权回调、事件存储生命周期、目标可见性及启动宿主差异。只有证据指向 JXA bridge/生命周期限制时，才做最小原生 helper 对照实验，并记录是否引入新技术的决策。
5. 明确拒绝共享状态未知、重复规则无法判定、参与者影响不明、只读或目标歧义的写入。现有 Calendar 唯一名称读取策略保留，不自动将旧名称授权迁移为稳定 ID 写入授权。
6. 若公开接口无法满足严格判定要求，形成决策记录：继续拒绝该类对象，或提出用户显式声明容器用途的授权方案及其残余风险。后者改变安全契约，必须由用户明确选择后更新计划，不能默认采用。

验收：每项拟开放写入均有可执行的支持/拒绝矩阵；稳定标识或安全条件不成立的动作继续关闭。该阶段未通过时不得以完成其他功能宣告版本达标。

### P3：接入受控修改与 Calendar 写入

依赖 P0–P2 对相应动作验收通过；动作可独立推进，不能由一个 adapter 的证据解除其他门禁。

- Reminders：扩展 provider 类型、固定写入脚本和 `src/operations/reminders.ts`，支持普通提醒标题、备注、截止日期修改及完成。
- Calendar：增加独立 writer 与操作服务，先接入个人单次事件创建，再在稳定目标定位成立后接入修改。
- 计划绑定客户端、容器、目标 ID、修改字段、预期状态指纹、授权策略版本及有效期；提交前重新校验权限、目标和支持形态。状态变化返回冲突，不静默覆盖；公开接口没有原子条件写入时须说明仍存在的竞态边界。
- 复用既有持久化意图、审批、幂等、核验与未知结果流程；需要 schema 迁移时保留旧计划的安全解释，不重新执行旧未决操作。
- 同步更新 `src/policy/`、`src/transports/local/handlers.ts`、MCP schema、管理审批预览及各 provider capability；按动作展示可用性与拒绝原因。

验收：覆盖并发提交只执行一次、撤销、计划过期、跨容器、指纹冲突、重复/共享拒绝、未知结果、日期/时区/DST；真实集成测试仅处理专用容器内连接器创建的对象。

### P4：权限、管理端与存储验证

- 验证终端、后台服务、目标 MCP 客户端、最终安装路径、服务重启与版本升级的 TCC/Apple Events 权限归属；覆盖首次授权、拒绝和重新授权，不重置 TCC 数据库。
- 管理端分别显示系统权限、客户端授权与实际动作能力；补充版本、协议、最近脱敏错误、未决操作和存储占用诊断。
- 完成范围编辑和凭证轮换；范围收缩后使受影响的未执行计划失效，旧凭证失效，新凭证仅在可信管理流程中交付。
- 使用小阈值和磁盘数据库验证审计清理、导出、WAL checkpoint、空闲页及实际占用；保留未决操作，对新写入施加已有预算约束。

验收：最终启动链路的授权可重复；用户能区分系统拒绝与连接器拒绝；管理入口鉴权回归通过；实测磁盘行为与文档一致。

### P5：文档与发布候选

- 先修正文档中的现状矛盾和恢复结论，再随各阶段更新能力矩阵、双语 README、首次任务流程、已知限制和诊断说明。
- 以实测结果确定 macOS/Node/架构支持矩阵，固定最终依赖；未验证平台不宣称支持。
- 扩展 `scripts/release-verify.mjs`：检查实际打包后的 CLI、全部注册脚本、管理静态资源和运行依赖，并执行 `--help`、`version`、`doctor` 冒烟验证。
- 确认发布仓库、tap、许可证及签名方案；先生成可审查产物和 Formula，完成全新安装、升级、重启和卸载测试。用户首次运行不需要安装 npm 依赖。
- 发布顺序为准确 tag/commit 校验 → 完整构建验证 → GitHub Release → tap 更新；普通卸载保留用户状态数据。
- 若 Formula 无法提供可接受的权限归属，基于安装实验评估签名应用包/Cask，并更新方案。
- 邀请目标用户验证安装和首次受限任务；沿用原计划的 10–20 位用户验证目标，记录实际参与数、成功率与问题。邀请和公开发布按用户授权执行。

验收：最终包在支持矩阵内完成首次受限任务与升级测试；文档准确；Release/tap 未执行或失败必须明确记录，不能以本地打包通过代替发布完成。

## 4. 执行顺序与交付物

| 顺序 | 交付物 | 进入下一阶段的条件 |
| --- | --- | --- |
| P0 | 恢复修复、历史探针对账记录、对应回归测试 | 恢复目标可精确确认，未决结果有明确记录 |
| P1 | 分阶段探针、超时诊断、真实运行证据 | 拟支持动作可重复核验，故障保留未知语义 |
| P2 | 支持/拒绝矩阵、Calendar 定位及技术决策记录 | 对应动作的安全条件和身份定位成立 |
| P3 | 提醒修改/完成、Calendar 创建/修改服务链路 | 核心测试及专用容器原生验收通过 |
| P4 | 安装权限矩阵、管理诊断、授权交互与磁盘验证 | 最终启动链路和管理流程通过 |
| P5 | 双语文档、发布候选、Formula、安装和用户验证记录 | 发布门禁全部通过 |

P4 的管理诊断、存储测试及 P5 的文档修正可在原生问题调查期间推进；不得跳过原生能力门禁提前开放写入。每完成一个切片，更新进度文件，记录代码、测试、证据、未决事项与下一步。

## 5. 阻塞项与处理原则

| 问题 | 当前判断 | 处理与退出条件 |
| --- | --- | --- |
| 恢复遗漏更新后标题 | 已定位的代码问题 | P0 修复并补齐回读证据 |
| Reminders 超时 | 根因未知，未证明不可解决 | P1 定位阶段；无法稳定通过则保持/收紧门禁 |
| Calendar 稳定标识及可见性 | 当前方案未验证成功 | P2 对照实验；失败时明确记录无法支持的操作 |
| 共享/重复状态可靠判定 | 可能是公开接口能力边界 | 验证替代路径；若需改变授权契约，提交明确产品决策 |
| 安装权限与分发 | 尚未完成验证 | P4/P5 最终安装实验，必要时调整打包方案 |

目前没有证据证明整个项目不可实现，也不能保证当前严格安全契约下所有原定写入都可实现。若必须能力无法成立，应先明确调整版本范围和验收条件，不静默删减功能或宣称完成。

## 6. 非范围与验证边界

不增加任意脚本执行、远程 MCP、跨设备同步、既有 Apple 数据删除、重复系列编辑、邀请管理或共享 Notes 写入；不读取私有数据库、修改 TCC、关闭系统保护或要求全磁盘访问。

测试清理仅处理明确授权容器内、能确认由连接器生成的探针。无数据测试、mock 测试、脚本语法检查和真实原生验收分别记录；只在代码变化或新问题需要时重复相关检查，不以通过数量替代能力证据。
