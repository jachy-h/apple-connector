# v0.1.1 实施进展

更新日期：2026-09-06。对应计划：[v0.1.1-plan.md](./v0.1.1-plan.md)。

## 当前状态

实施中。v0.1.0 的原型基线保持冻结；当前从 Reminders 的原生受控更新探针开始，不提前向服务公开既有对象写入。

## 本轮结果

- 已新增 `diagnostics.remindersUpdateCrud`：仅在调用方给出的清单中创建带请求 UUID 的提醒，按返回的稳定 ID 更新标题、备注、date-only 截止日期和完成状态，回读核验后删除。
- 固定 JXA 注册表、原生测试入口及静态语法检查已同步更新；`npm run check:jxa` 与 `npm test`（53 项）均通过。
- 在本机 `Agents` 清单运行该探针未在 60 秒原生时限内返回可验证结果。因此结果按 unknown 处理，未将更新/完成 writer、MCP 工具或 capability 标为可用。
- 旧 M0 Reminders CRUD 探针也在同一清单出现同步阻塞；这说明需要先完成超时结果对账与清理证据，不能将“脚本可解析”当作真实写入能力。
- 批量按标题前缀清理残留探针不具备足够的目标确认性，已明确排除；后续恢复只能使用调用时已持有的稳定提醒 ID。
- M1 探针现要求调用方在写入前提供 UUID，并以此构造测试标题；未来即使 native outcome 为 unknown，调用方仍可精确定位单一探针，不依赖原生请求 ID 或模糊匹配。
- 已增加精确恢复删除：仅接受调用方预先持有的 UUID，限定到一个明确清单；零个匹配为无操作，多个匹配一律拒绝。
- 2026-09-06：以 UUID `5f79e1ab-7e5f-43a5-973a-156114c5843e` 运行 M1 探针仍未返回可验证结果；随后的精确恢复删除返回 `removed: false`。因此该 UUID 没有可确认的残留对象，但更新/完成结果仍是 unknown，不能据此开放能力。

## 已继承的证据

- 三个 `Agents` 专用容器的最小创建→限定回读→删除探针已通过。
- Calendar 的唯一名称范围读取、Reminders/Notes 受限读取、Reminders/Notes 创建已在 v0.1.0 基线中验证。
- 不可将这些证据扩展为既有对象修改、Calendar 写入或共享/重复对象支持；每项须单独验证。
