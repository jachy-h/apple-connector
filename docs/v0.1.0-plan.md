## 1. 目标与产品判断

Apple Connector 是运行在用户 Mac 上的个人数据连接器，让已有 agent 在明确授权范围内访问 Apple 日历、提醒事项和备忘录。项目提供确定性的执行、权限控制与操作记录，不提供聊天、模型调用或自然语言规划功能。

首批用户是已经经常使用 agent，同时依赖 Apple 日历、提醒事项和备忘录的个人用户。首版验证以下价值：

1. 将对话中的待办写入指定提醒事项清单，减少手工搬运。
2. 读取近期日程与待办，辅助安排一天。
3. 将 agent 的整理结果保存成新的 Apple 备忘录。
4. 用户可以看到每个客户端的授权和实际操作，并随时撤销权限。

市场上已有 Apple MCP、原生菜单栏连接器和提醒事项 CLI。因此，“接入三个 Apple App”“支持 MCP”“有界面”属于基础能力，不作为独有卖点。首版需要验证的差异是安装是否容易、授权是否清楚、写入是否可靠、记录是否有助于建立信任。现阶段不假设付费意愿或市场规模已经得到证明。

## 2. 已确定的技术方向

采用 **TypeScript + Node.js + JavaScript for Automation（JXA）**。不预先引入 Go、Swift、Electron 或独立云服务。

| 层次 | 技术与职责 |
| --- | --- |
| 应用服务 | TypeScript / Node.js：MCP、CLI、授权、操作编排、审计、管理 API |
| Apple 适配层 | 固定 JXA 脚本，通过 `/usr/bin/osascript -l JavaScript` 执行 |
| 管理界面 | React + TypeScript + Vite，本地静态资源随包分发 |
| 存储 | SQLite：配置、授权、操作状态和审计；具体驱动在原型阶段确定 |
| 分发 | GitHub Release + 自有 Homebrew tap；首选 Formula |

Node.js 与 JXA 是两个运行环境。Node.js 中不能直接使用 JXA 的 `Application()`、`ObjC` 等能力；双方通过结构化协议通信。JXA 脚本应单独构建、检查和测试，不能直接依赖 Node.js API 或 npm 模块。

AppleScript 与 JXA 通过 Apple Events 调用应用脚本字典，在这一层能力通常相近，但类型转换、错误行为和兼容性不保证完全一致。首版优先 JXA，不同时维护两种脚本语言。

日历和提醒事项首先验证应用脚本接口；JXA 经 Objective-C bridge 调用 EventKit 是候选实现，不视为已经验证。Notes 使用其脚本接口。最终由能力原型决定每个 adapter 的路径，对外接口保持稳定。

只有出现明确且难以合理解决的桥接、权限或生命周期问题，才评估为对应模块增加 Swift。不得因某个 adapter 需要原生实现而重写整个服务。

## 3. v0.1.0 范围

### 3.1 数据操作

| 数据源 | 必须支持 | 首版限制 |
| --- | --- | --- |
| 日历 | 列出允许的日历；按时间范围查询；创建普通个人事件；修改受支持的单次个人事件标题、时间、地点和备注 | 不修改重复系列、不管理邀请、不编辑共享或含参与者的事件、不删除事件 |
| 提醒事项 | 列出允许的清单；查询；创建；修改普通提醒的标题、备注、截止日期；完成普通提醒 | 不管理清单、不操作重复提醒的复杂规则、不实现标签、子任务、位置触发和删除 |
| 备忘录 | 列出允许的文件夹；搜索标题及有限摘要；读取普通笔记；创建简单笔记 | 不修改已有笔记、不删除、不编辑附件或复杂富文本；跳过锁定笔记；首版不写共享笔记或共享文件夹 |

上述写入范围以 adapter 能明确判定对象是否受支持为前提。无法判定是否为重复、共享或含外部影响的对象时，保守拒绝写入，不猜测。

“普通事件/提醒”由明确的支持矩阵定义。若原型无法可靠实现某项必须能力，需要在实现前更新本计划和版本范围，不静默降级。

### 3.2 安装与使用

- Homebrew 安装，无需用户自行安装项目 npm 依赖、编译 Swift 或配置数据库。
- CLI 提供 `setup`、`start`、`stop`、`status`、`doctor`、`mcp`、`version`、`--help`。
- `start` 启动用户级本地服务；首版不使用 root 系统服务，不默认添加开机自启。
- `mcp` 是轻量 stdio 入口，连接同一后台服务；服务未启动时返回明确提示。
- 管理网页支持查看授权、调整策略、审批、查看记录和诊断。
- 所有 agent 访问都经过统一应用服务，不提供绕过授权的直接数据 CLI。
- 不支持远程 agent、公网 HTTP MCP、跨设备授权同步或 iOS 服务端。

CLI 名称暂定为 `apple-connector`，仓库和 tap 地址在首次发布前确定。

## 4. 用户流程与授权

### 4.1 首次使用

1. 用户安装并运行 `apple-connector setup`。
2. 设置流程启动服务，建立本地管理会话并打开管理网页。
3. 用户按需启用数据源，执行权限检查或由明确操作触发系统授权。
4. 在可信管理会话中选择可访问的日历、清单或文件夹。
5. 创建客户端，分配权限，取得 MCP 配置和独立凭证。
6. 执行一次受限查询或创建操作，在系统 App 和操作记录中核对。

默认不授权任何客户端。管理界面为选择范围所需的容器枚举属于用户管理操作，不能通过未授权 MCP 接口泄露。

### 4.2 两层权限

界面分别显示：

- **系统权限**：当前执行链路是否能访问 Apple 数据。
- **连接器权限**：某个客户端被允许访问的范围、动作和字段。

系统允许访问不等于 agent 获得访问权。EventKit 的读取需要完整访问权限，没有独立的系统只读权限，因此连接器需自行限制只读行为。Apple Events 路径的权限状态不完全等同于 EventKit；无法可靠查询时显示“尚未验证”，不能推断为已授权。

权限至少包含：客户端、数据源、容器白名单、动作、字段、到期时间和审批方式。使用真实凭证识别客户端，不信任客户端自报名称。

推荐预设：

| 预设 | 行为 |
| --- | --- |
| 只读 | 读取指定范围；可选择日历仅返回忙闲 |
| 收件箱写入 | 在指定清单/日历/文件夹创建受支持内容 |
| 受控编辑 | 修改或完成指定范围内的受支持对象，每次生成审批计划 |

用户可显式授予范围受限的自动修改权限，不对已授权低风险操作反复弹窗。批量上限必须由服务端执行，首版建议每个变更计划最多 5 个对象。

撤销权限后立即阻止新的访问，使未执行计划失效；已经发送给 Apple App 的操作不保证能取消，需要核验并记录结果。

### 4.3 安全边界

- 笔记正文、事件描述等是不可信数据，不作为权限指令执行。
- agent 不能使用 `user_approved: true` 等参数自行批准操作。
- 客户端凭证不能调用管理授权接口。
- 本地读取不等于内容不会进入云模型；返回给客户端后的传播不由连接器完全控制。
- 若 agent 具有同用户任意代码执行或其他直接 Apple 数据访问权限，可能绕过连接器。首版保证自身接口内的授权控制，不承诺隔离已控制本机用户环境的程序。

## 5. 架构与目录

```text
Agent → MCP stdio shim ─┐
                       ├→ 应用服务 → 授权 → 操作执行 → 数据源 adapter → JXA → Apple
管理网页 → 管理 API ────┘                 └→ 操作状态与审计
```

采用单仓库、模块化单体。不实现动态插件系统，也不为三个应用分别部署服务。

```text
src/
  cli/                     命令入口与服务生命周期
  transports/
    mcp/                   MCP 工具、stdio 客户端入口
    admin/                 管理 HTTP API 与会话
    local/                 后台服务本地通信
  application/             用例与跨数据源编排
  clients/                 客户端配对、凭证与身份
  policy/                  范围、字段、额度、审批判断
  operations/              计划、执行状态、幂等、核验
  audit/                   查询、导出与保留策略
  storage/                 SQLite 与迁移
  providers/
    calendar/              日历模型、校验、能力和 adapter
    reminders/             提醒事项模型、校验、能力和 adapter
    notes/                 笔记模型、格式与 adapter
  jxa/                     调用器、协议、超时与输出限制
scripts/jxa/
  calendar/
  reminders/
  notes/
web/                       React 管理界面
tests/                     单元、契约、集成和发布测试
docs/                      用户文档、支持矩阵与设计
scripts/release/            构建与发布校验
```

数据源模块互不调用；跨应用任务由 application 层编排。不把事件、提醒和笔记统一压成通用 `Item`，只共享查询分页、错误、计划和执行生命周期。

### 5.1 JXA 边界

- 使用固定脚本和显式操作白名单，不接收任意脚本源代码。
- 使用无 shell 的子进程参数调用；正文通过独立结构化输入通道传输，不拼接源代码，不放入可见命令行参数。
- 输入输出携带协议版本、request ID、操作类型和结构化结果。
- 校验输入大小、输出大小、类型、退出码和协议格式。
- 设定超时与并发上限；对同一数据源写操作串行调度。
- 超时后的写操作标记为结果未知并对账；杀死脚本进程不代表目标 App 已取消写入。
- 避免为每条记录启动一个进程；批量查询在受限的一次调用中完成。
- 不直接读取或修改 Apple 私有数据库，不要求全磁盘访问作为通用解决方案。

### 5.2 本地服务与管理端

stdio shim 通过仅当前用户可访问的本地 IPC 连接后台服务，并携带客户端凭证。IPC 文件权限不能替代客户端授权。

管理网页仅监听 loopback；采用独立管理会话、Host/Origin 校验和 CSRF 防护。首次管理会话通过本地 setup 引导建立，不设置默认密码，不把持久凭证放入 URL。前端资源本地分发，不使用外部 CDN。

状态数据建议位于 `~/Library/Application Support/AppleConnector/`，运行日志位于 `~/Library/Logs/AppleConnector/`，运行时文件位于受限用户目录。凭证存储方案在原型阶段确定，优先验证 Keychain；如采用受限文件，需明确同用户进程的访问边界。

## 6. 操作一致性与工具接口

写入统一经过：

```text
解析明确目标 → 校验范围与能力 → 生成不可变计划
→ 自动授权或用户批准 → 执行前重读与校验
→ 持久化执行意图 → 执行 → 读取核验 → 记录结果
```

- 审批绑定客户端、目标、参数、版本指纹、策略版本和到期时间。
- 执行前重新校验权限和对象状态；计划生成后不能替换参数。
- 原生接口可能没有原子条件写入，写前检查只降低冲突风险，不承诺绝对无覆盖。
- 日期模型区分全天日期、带时区时间和无具体时刻的提醒；不随意以 UTC 午夜代替日期。
- 对象 ID 仅作为定位依据之一，失效或重定位歧义时停止写入。
- 不承诺跨应用事务或一键恢复；逐项返回成功、失败和未知结果。
- 幂等键绑定客户端与请求内容。结果未知时不盲目重试，不宣称 exactly-once。

初始 MCP 工具集：

```text
connector.capabilities
calendar.list_calendars
calendar.list_events
reminders.list_lists
reminders.list
notes.list_folders
notes.search
notes.get
changes.prepare
changes.commit
operations.get
```

`changes.prepare` 使用严格枚举的操作 schema，例如创建事件、修改单次事件、创建提醒、修改提醒、完成提醒、创建笔记。`changes.commit` 只接受计划引用，不重新接收可替换的修改内容。

查询支持范围、分页、字段选择和结果上限。忙闲模式必须删除标题、正文、地点和参与者等字段；筛选、检索和缓存均不能绕过范围检查。Notes 默认不全库索引、不复制全文数据库。

标准错误至少包含 `permission_denied`、`approval_required`、`ambiguous_target`、`conflict`、`unsupported_operation`、`timeout`、`outcome_unknown`、`service_unavailable`。MCP 和 CLI 不向用户直接暴露难以理解的原始脚本异常。

## 7. 审计与日志

操作审计、运行日志、幂等及操作状态分开管理。

| 类型 | 默认策略 |
| --- | --- |
| 审计 | 保留 30 天；最多 20,000 条；审计存储预算约 50 MiB，达到任一限制即清理最旧记录 |
| 运行日志 | 单文件 5 MiB；最多 3 个文件（含当前文件）；最长 7 天 |
| 操作与幂等状态 | 独立保留；终态幂等记录建议 30 天，未决操作不因审计清理而丢失 |
| 恢复快照 | v0.1.0 不提供通用恢复，不持久化完整修改前正文 |

审计字段：时间、客户端、操作 ID、数据源、动作、目标引用、涉及数量、修改字段名称、授权依据、结果、错误码和耗时。

- 记录成功写入、失败、拒绝、授权变更；读取记录范围和数量，不记录返回正文。
- 高频重复读取可在界面聚合，仍保留有限周期内可定位的操作记录。
- 不持久化完整标题、笔记正文、token 或完整工具输入输出。
- Debug 显式开启、限时自动关闭，继续执行敏感信息脱敏。
- 界面支持筛选、导出、清空和显示占用量；导出前提示内容范围。
- SQLite 清理同时考虑 WAL、checkpoint 和空闲页回收，区分逻辑记录预算与实际磁盘占用。
- 无法持久化执行意图时拒绝新的写操作；执行后记录失败则进入明确的未决状态，提示用户核验。
- 未决状态达到存储预算时阻止新写入并提示处理，不无限增长或静默删除。
- 不宣称本地记录具备合规防篡改能力。

## 8. 管理界面

首版包含四个页面：

1. **连接与授权**：客户端、凭证轮换、范围、动作、到期时间、立即撤销。
2. **数据源**：系统权限、能力状态、容器选择、已知限制与重新检查。
3. **操作记录**：按时间、客户端、数据源、结果筛选，查看授权依据和人类可读摘要。
4. **待确认**：目标、旧值与新值、影响范围、有效期、批准或拒绝。

审批预览按需读取必要字段，不把敏感差异自动复制到长期审计。提供全局暂停操作入口。诊断页或面板展示服务版本、脚本协议、权限检查和最近错误，不显示凭证。

## 9. 发布方案

参考 `../umbra-gate/.github/workflows/release.yml`、`scripts/release-verify.sh` 和 `Makefile` 的流程，保留“准确 tag commit → 完整生产构建与测试 → Release → tap 更新”的顺序。

### 9.1 首选：Homebrew Formula

- 发布构建后的 JS、JXA 脚本、前端静态文件、启动入口与必要运行依赖元数据。
- Formula 声明 Node 依赖，在构建/打包阶段完成依赖准备；用户首次运行不执行 `npm install`。
- 原型期选择并固定受支持的 Node LTS 范围，不追随未经验证的新版本。
- 如使用 SQLite 原生扩展，必须处理 ABI、架构与安装方式；优先降低原生依赖发布负担。
- 若产物全部与架构无关，可发布单一归档；如包含原生产物，则分别构建 arm64 和 x86_64。发布支持声明以实际验证为准。
- 生成 SHA-256，发布 GitHub Release 后更新自有 tap 的版本、URL 和校验和。
- 不要求进入 homebrew/core；不自动上传用户数据或启用自启动。

### 9.2 转向 Cask 的条件

如果 Formula 启动链路无法提供可接受的权限归属、后台运行或升级体验，则评估签名应用包，并通过 Cask 安装。JXA 也可打包为脚本应用，不能把“必须用 Swift”作为前提。

这一变更必须经过原型验证，并更新安装、构建、签名与公证方案。Homebrew 不替代系统隐私授权；不把关闭 Gatekeeper、修改 TCC 数据库或禁用系统保护作为安装步骤。

### 9.3 发布门禁

- tag 必须解析为预期的准确 commit，手动发布也遵循同一规则。
- 先完成前端构建、TypeScript 编译、脚本与协议检查、测试，再发布。
- macOS 上验证 JXA 和最终安装包；Linux CI 可测试纯 TS 核心，但不能替代 macOS 验证。
- README.md 与 README_zh.md 反映当前命令、权限、安装、日志默认值和限制。
- 对照最终包执行 `--help`、`version`、`doctor` 和前端资源检查。
- 检查全新安装、升级、服务重启和卸载行为；普通卸载保留用户数据，数据删除由用户显式操作。
- tap 更新仅在 Release 成功后执行，可单独重试；缺少凭证或更新失败应明确报告，不伪装为 Homebrew 已更新。

## 10. 实施阶段与验收

### M0：能力与安装原型

产出脚本实验、能力矩阵、启动/权限矩阵和选型记录。

- 验证三个数据源的最小查询与创建，以及日历/提醒的受限修改。
- 对比日历/提醒的 Apple Events 路径与 JXA EventKit bridge，验证授权回调和查询行为。
- 验证终端、目标 MCP 客户端、后台进程、Formula 安装路径与升级后的权限归属。
- 验证超时后的结果核验、日期语义、简单笔记格式往返。
- 明确支持的 macOS、Node 和架构范围，选择 SQLite 驱动及凭证存储方案。

**通过条件**：确定一条可解释、可重复的安装与授权路径；必须能力可实现；已知不支持情况可被识别并拒绝。未通过时先调整 adapter 或发布方案，不继续堆积产品功能。

### M1：服务与一个完整用例

- 建立目录、共享 schema、服务生命周期和 MCP stdio 入口。
- 实现客户端身份、范围授权、SQLite 迁移和 JXA 调用器。
- 打通“创建提醒 → 核验 → 审计 → 客户端查询结果”。

**通过条件**：未授权请求被拒绝；正常创建只产生预期对象；重复请求可识别；结果未知不盲重试。

### M2：三个数据源与写入控制

- 完成范围内的三个 adapter 和 capability 报告。
- 实现变更计划、审批、执行前重读、逐项结果和撤销生效。
- 覆盖范围逃逸、字段泄露、计划参数替换、并发修改、重复对象和超时场景。

**通过条件**：所有入口走统一权限和执行链；不支持操作有明确错误；没有以标题猜测唯一目标的写入。

### M3：管理界面与有界审计

- 完成四个管理页面、管理会话和请求保护。
- 实现日志轮换、审计清理、导出、空间显示和诊断。

**通过条件**：用户能理解实际生效权限，完成审批和撤销；agent 凭证不能提升自身权限；容量策略可通过小阈值测试验证。

### M4：候选版本与真实用户验证

- 完成发布流水线、自有 tap、双语文档和最终包验证。
- 邀请 10–20 位目标用户，观察安装、首次任务和数周内的重复使用。
- 自愿收集脱敏诊断和访谈反馈，不默认上传操作记录。

**发布条件**：支持矩阵内的安装与操作通过；已知限制公开；越权、重复写入和不明确结果处理没有未解决的阻断问题。

## 11. 测试原则与产品指标

纯 TS 测试覆盖授权、计划状态机、幂等、日志保留和协议校验；adapter 契约测试使用脱敏固定夹具。实际 Apple 集成测试在专用测试账户或明确指定的测试容器中执行，不默认操作开发者真实数据。

真实 TCC 弹窗和客户端权限归属需要交互验证，不声称普通 CI 已覆盖。写入测试限制目标容器，并核验实际结果。重点测试引号、换行、Unicode、超长内容和类似脚本指令的正文，确认内容始终被当作数据。

产品验证记录：安装到首次任务成功率、完成所需步骤、每周重复任务用户数、写入成功率、人工纠正次数、重复写入次数、权限修复频率、未决操作与日志占用情况。GitHub stars 和工具数量不作为主要成功指标。

商业模式暂不进入 v0.1.0。核心授权和审计不收费锁定；许可证在首次公开发布前确定，优先评估 MIT 或 Apache-2.0。远程访问、团队控制和商业支持需后续需求证明。
