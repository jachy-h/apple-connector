# Apple Connector v0.9.6 计划：Agent Skill 工作流修订

更新日期：2026-09-09
状态：Git push 范围修订已获维护者批准
进度：[v0.9.6-progress.md](./v0.9.6-progress.md)

## 目标

以简洁、可执行且与当前 CLI 契约一致的语言重写 `skill/SKILL.md`。当用户表达“提醒我……”或等价提醒意图时，Agent 必须把它视为同步 Apple Reminders 的明确请求：新提醒使用 `reminder create`，明确指向既有提醒的变更使用相应的 `update`、`complete` 或 `delete`；不能只在对话中承诺提醒。目标、清单、日期、时间或时区不明确时，先向用户澄清，不猜测写入。

## 实施范围

### 1. 收紧意图和目标选择

- 保留 Calendar 用于有起止时间的安排、Reminders 用于提醒和待办的区分。
- 明确“提醒”意图必须通过公开 `apple-connector` CLI 同步到 Reminders，并仅在 CLI 返回确定结果后报告成功。
- 修改、完成、删除前先读取；标题只用于寻找候选，真正写入必须使用唯一确认的容器 ID 和对象 ID。多个匹配、缺少 ID 或分页尚未查完时停止并澄清。

### 2. 给出最小但完整的 CLI 契约

- 所有机器调用使用 `--json`；onboarding 完成后保留 `credentialFile` 路径，并在每个业务命令和 `operation get` 中显式传入 `--credential-file`，绝不读取文件内容。
- 简洁列出 Calendar/Reminders 的查询与写入命令模板、必填参数、分页 `nextOffset` 处理和写入返回状态。
- 修正 reminder due 格式：date-only 为 `{ "kind": "date", "date": "YYYY-MM-DD" }`，不带时区；指定时刻为 `{ "kind": "instant", "at": "RFC3339-with-offset", "timeZone": "IANA" }`。
- 明确 Calendar 和 Reminder 的 update 是完整替换：先从读取结果复制所有未修改字段，只改用户要求的字段，避免清空正文、地点、备注或状态。
- 私密字段写入权限为 `0600` 的临时 JSON 文件；保留到操作进入确定终态或恢复完成，再删除。

### 3. 补齐状态机和恢复逻辑

- onboarding 覆盖 `pending`、`configured`、`expired` 和 `failed`，并保持“用户回复完成前不访问页面、不轮询、不调用业务命令”的边界。
- 写入返回 `prepared` 时，保存 operation ID 和原始请求，向用户提供 approvals 链接并等待；批准后使用完全相同的 payload 和 idempotency key 重新提交，由现有幂等状态机执行。
- `outcome_unknown` 时禁止更换 key 或 payload；使用完全相同的请求和 key 获取持久化 operation ID/状态，再通过带 credential 的 `operation get` 查询。
- 区分 `succeeded`、`prepared`、`failed`、`expired`、`cancelled` 和 `outcome_unknown`，不得把“已提交”误报为“已写入”。

### 4. 回归测试与版本契约

- 新增 Skill 契约测试，至少覆盖 frontmatter、提醒意图、显式 credential、`--json`、两种 due 结构、完整替换保护、审批和未知结果恢复规则。
- 同步 package/lockfile、native helper 版本和 `release:verify` 至 v0.9.6；确认更新后的 Skill 仍包含在 npm tarball 中。
- 不改变 CLI、服务、授权、数据库或原生写入语义。

### 5. 发布准备、Git 推送与手工 npm 交接（2026-09-09 再修订，已获批准）

- 将当前工作树作为从远端 v0.8.3 累积到 v0.9.6 的发布候选；提交前审计全部已跟踪、删除和新增文件，排除凭证、缓存、临时状态、诊断日志及无关文件，不擅自丢弃现有改动。
- 重新执行 `npm run release:verify` 与 `git diff --check`，并核对 CLI、native helper、manifest、lockfile 和 tarball 均为 v0.9.6。
- 检查 `gh auth status`、Git remote、目标 tag 不存在及 npm 包的匿名 registry 状态。npm 登录、账号/scope 权限、2FA 和 publish 全部由维护者在手工发布时检查；Agent 不要求、读取或验证 npm 凭证，`npm whoami` 的 E401 不阻塞本地准备。任何 token、OTP 或 credential 都不得写入日志、文档或命令参数。
- 创建单一发布提交 `release: prepare v0.9.6`，在该准确提交上创建本地 annotated tag `v0.9.6`；确认 tag、HEAD 和临时 tarball 对应同一版本基线。
- 在仓库外的临时目录生成 tarball，记录文件数、大小、SHA-256 和 npm integrity，完成最终本地安装验证后删除临时产物。
- Agent 不执行 `npm publish`。向维护者交接准确 commit、tag、校验结果以及手工命令 `npm publish --access public`；不要求或接收 npm token/OTP。
- 本地验证和 tag 检查通过后，推送发布提交到 `origin/main`，再推送固定的 annotated tag `v0.9.6`；回读远端并确认 main/tag 指向同一发布提交。仍不创建 GitHub Release。
- npm 版本不可覆盖。若维护者报告手工发布失败，不修改版本、移动 tag、绕过 2FA 或自动 unpublish；先记录实际 registry 状态再制定后续步骤。

## 验证标准

1. 目标 Agent 收到明确“提醒”请求时会实际调用 Apple Connector 同步 Reminders，而不是仅口头承诺。
2. Skill 中的命令参数、due JSON 和写入状态与 v0.9.6 CLI 实现一致。
3. 更新不会丢失用户未要求修改的字段；歧义、审批和未知结果不会被误报为成功。
4. credential/token 不进入命令行或输出；私密业务字段只经 owner-only 输入文件传递。
5. `npm test`、`npm run check:jxa`、`npm run release:verify` 和 `git diff --check` 通过。
6. 本地发布提交与 annotated tag `v0.9.6` 指向同一准确 commit；工作树在提交后干净。
7. 临时 tarball 的版本、文件清单、SHA-256、npm integrity、隔离安装后的 CLI 与 Skill 路径验证均已记录。
8. 远端 `main` 和 `v0.9.6` 指向同一发布提交；交接明确停在 `npm publish` 之前，GitHub Release 和 npm registry 均未由 Agent 修改。
