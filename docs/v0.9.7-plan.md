# Apple Connector v0.9.7 计划：修复 native helper 长期运行的内存泄漏

更新日期：2026-11-13
状态：已完成（源码、测试、版本、文档、发布验证与服务重启）；后续仅需长期观察 footprint
进度：[v0.9.7-progress.md](./v0.9.7-progress.md)

## 结论（先给答案）

是程序问题，不是 EventKit 或系统统计误差。

`dist/native/apple-connector-helper` 是一个长期存活的单进程 JSONL helper。它的主循环每处理一条请求，EventKit/Foundation 产生的 autoreleased 临时对象都落在**从未 drain 的 autorelease pool**里。helper 从 2026-09-10 启动至今运行约 63 天，累计占用约 **5.4 GB**（几乎全部被换出到 swap），且随请求数线性增长。

## 现场证据

运行中的进程（PID 92172，父进程 92166）：

```text
$ ps -o pid,rss,vsz,%mem,etime,command -p 92172
  PID    RSS      VSZ %MEM     ELAPSED COMMAND
92172   5152 435366208  0.0 63-22:06:27 .../apple-connector-helper
```

RSS 只有 5 MB，是因为页面已被换出；真实占用要看 physical footprint：

```text
$ footprint 92172
apple-connector-helper [92172]: 64-bit    Footprint: 5518 MB
  Dirty      Clean  Reclaimable    Regions    Category
5492 MB        0 B          0 B       1380    MALLOC_SMALL
  22 MB        0 B          0 B         51    MALLOC metadata

$ vmmap -summary 92172
Physical footprint:         5.4G
Writable regions:  Total=5.5G written=5.4G resident=3221K swapped_out=5.4G
```

`heap` 显示泄漏主体是 Foundation 桥接临时对象，而非 helper 自身的数据结构：

```text

  126187   516861952  4096.0  @autoreleasepool content
  116272     5581056   48.0   Swift.ManagedBuffer<Foundation.Calendar, ...>
  116272     1860352   16.0   _NSSwiftCalendar
  114799    22041408  192.0   CFDateComponents
  114799     1836784   16.0   NSDateComponents
```

约 6340 万个 80 字节的 `Swift.StringStorage`（5.07 GB）和 12.6 万个 autorelease pool content 页（0.52 GB）与请求次数成正比，符合“每条请求留下 autoreleased 临时对象”的特征。

## 复现与定位（本机实测，未修改仓库源码）

用现有 `dist/native/apple-connector-helper` 通过 stdin 批量发送请求，记录 `/usr/bin/time -l` 的最大 RSS：

| 输入 | 请求数 | 最大 RSS |
| --- | --- | --- |
| `hello` | 100,000 | 16.9 MB（无增长） |
| `reminders.listLists` | 2,000 | 20.7 MB（无增长） |
| `calendar.listEvents`（71 个事件） | 500 | 60.8 MB |
| `reminders.list`（Inbox，limit=100） | 2,000 | 844 MB |
| `reminders.list`（Inbox，limit=50） | 500 | 1.27 GB |
| `reminders.list`（Inbox，limit=1） | 2,000 | 2.64 GB |

把 `main.swift` 复制到 `/tmp`，仅在主循环体外套一层 `autoreleasepool { ... }` 重新编译后：

| 输入 | 请求数 | 最大 RSS |
| --- | --- | --- |
| `reminders.list`（Inbox，limit=50） | 500 | 34.7 MB |
| `reminders.list`（Inbox，limit=50） | 2,000 | 34.7 MB（保持平稳） |
| `calendar.listEvents`（71 个事件） | 500 | 21.7 MB |

结论：泄漏来自主循环缺失 autorelease pool，`autoreleasepool` 修复后吞吐一致、内存平稳。`reminders.list` 最严重，因为 `store.fetchReminders` 每次都会把整个列表的提醒桥接成 Swift/Objective-C 对象，而分页只返回其中一页。

## 根因

`native/Sources/AppleConnectorHelper/main.swift` 末尾：

```swift
let helper = Helper(); let decoder = JSONDecoder(); let encoder = JSONEncoder()
while let line = readLine(strippingNewline: true) { ... }
```

纯 Swift 可执行文件不会在 `main` 或循环迭代边界自动建立/排空 autorelease pool。EventKit、`ISO8601DateFormatter`、`Calendar.current` 等每次请求产生的 autoreleased 对象一直挂在默认池上，直到进程退出才释放。服务端长期不回收 helper，于是内存随请求数单调增长。

## 实施范围

### 1. 修复 helper 主循环（唯一必需的源码改动）

- 在 `native/Sources/AppleConnectorHelper/main.swift` 中把“单行请求 → 单行响应”的处理提取为独立函数，主循环每轮执行：

```swift
while let line = readLine(strippingNewline: true) {
  autoreleasepool { respond(to: line) }
}
```

- 保持 JSONL 协议、请求/响应字段、错误码、超时和写入幂等语义完全不变。
- 不改变 EventKit 调用顺序、分页或校验逻辑；不引入跨请求状态。
- 可选加固（需单独确认）：`EventKitHelperClient` 在 helper 空闲时按请求数（例如 5,000 次）主动重启子进程，作为未来回归的保险。该改动会增加生命周期复杂度，默认**不做**，除非维护者要求。

### 2. 回归测试

- 新增 `tests/native/memory.test.ts`：
  - 仅在 macOS 且设置 `APPLE_CONNECTOR_REMINDERS_TEST_LIST_ID` 时运行，沿用既有 native 测试的测试列表约定。
  - 用 helper 的 `reminders.createVerified` 在该列表创建固定数量的 UUID 探针提醒（例如 60 条），`finally` 中全部 `reminders.deleteVerified`。
  - 通过 `EventKitHelperClient` 连续发送固定次数（例如 200 次）`reminders.list`，用子进程 `footprint -pid`（解析 `Physical footprint`）或 `ps` 采样，断言 footprint 增量低于标定阈值。
  - 阈值在实施时用修复前/后实测数据标定，目标：修复后稳定通过，回归时按当前泄漏速率必然失败。
- 新增不依赖权限的循环基线用例：连续 5,000 次 `hello`，断言 footprint 不随请求数增长。
- 保留既有 `npm test` 与 `npm run test:native` 门禁，新增测试不得依赖个人日历/提醒的生产数据，只使用显式 opt-in 的测试列表。

### 3. 版本与发布契约

- 版本升级到 v0.9.7：`package.json`、`package-lock.json`、helper `hello` 返回的 `helperVersion`、`scripts/release-verify.mjs` 期望版本。
- 重新构建 `dist/native/apple-connector-helper`（本任务会生成产物，但只在批准后执行）。
- `docs/native-validation.md` 增加“长期运行内存”验证条目和 `footprint` 检查方法。

### 4. 运维处理（不属于源码改动）

- 当前运行中的 helper 已占用 5.4 GB，即使代码修复也不会自动释放；发布后需重启服务回收：
  `apple-connector stop && apple-connector start`（或维护者当前使用的启动方式）。
- 在修复版本安装前，如系统 swap 压力明显，可先重启服务临时缓解；重启前需维护者确认没有进行中的写入操作。

## 不做的事

- 不改 CLI、IPC 协议、存储 schema、审批/幂等状态机或 Web 管理页。
- 不把 helper 改成按请求启动的一次性进程（会显著增加 EventKit 初始化延迟和 TCC 交互）。
- 不在未标定的情况下使用宿主机绝对内存阈值做进程自动重启；如需上限，走第 1 节的“可选加固”。
