# Apple Connector v0.17.0 计划：用自签名 App 承载 macOS 权限身份

更新日期：2026-11-19

状态：已批准并实施（2026-11-19）；自签名证书已创建，TCC 持久性等待用户完成一次日历授权后验收

进度：[v0.17.0-progress.md](./v0.17.0-progress.md)

## 问题

当前 helper 以普通子进程方式由 Node 服务启动。macOS TCC 不会把 EventKit 权限记在 helper 的代码签名上，而是记在“负责进程”（responsible process）所属的 App 上。实测证据：

- 新编译一个只查询 EventKit 状态的 ad-hoc 二进制（全新 cdhash），运行结果与 helper 完全一致：`calendar=0 reminders=3`。新二进制不可能自己持有授权，说明权限来自父进程继承。
- 运行中的服务环境含 `__CFBundleIdentifier=ai.opencode.desktop`；OpenCode.app 有提醒事项授权，没有日历授权。
- 最小 `.app` 用 `open` 启动后查询得到 `0/0`：只有被 LaunchServices 当作独立 App 启动的 bundle，才有自己的 TCC 身份。
- 仓库既有的 [distribution-decision.md](./distribution-decision.md) 已经记录过“TCC 按负责进程记录，权限归启动服务的终端 App”。

因此，只给 helper 自签名不会改变权限归属。v0.17.0 要让 **Apple Connector 自己成为负责进程**：把现有 helper 二进制装进一个固定 bundle id、使用稳定自签名证书的 `.app`，由 LaunchServices 启动；helper 增加 Unix socket 模式，Node 服务通过 socket 调用它，不再以 stdio 子进程方式启动。

这样系统设置里显示的是 Apple Connector，日历/提醒事项授权也只属于它；升级或重建只要签名证书和 bundle id 不变，授权就会保留。

## 目标

1. Calendar / Reminders 的 TCC 权限归属于 `Apple Connector.app`，不再归属 OpenCode、Terminal 或其他宿主 App。
2. 重新构建、版本升级、安装路径变化后，只要证书和 bundle id 不变，授权保持有效。
3. 保持 helper 的 JSONL 协议、EventKit 操作实现、错误码和 Node/CLI 业务契约不变。
4. 不购买 Apple Developer Program，不做公证；npm/本机源码安装仍是唯一分发方式。
5. 文档清晰覆盖：证书创建、构建签名、授权迁移、验证、排障、轮换与分发边界。

## 非目标

- 不引入 Developer ID、notarization、Homebrew Cask 或公开 `.app` 分发。
- 不把 Node 运行时打包进 App，不改变 Node 服务的启动方式（仍由 CLI 启动）。
- 不修改 EventKit 业务逻辑、Agent 授权策略、数据库结构、审计格式或 RPC 业务方法。
- 不支持多用户并发；同一用户多 state dir 仅保证 `open -n` 能各自启动一个实例。
- 不自动创建钥匙串证书；证书创建走文档步骤，构建脚本只检测和签名。

## 架构

```text
apple-connector start
  ├─ 检查 <state>/helper.sock 是否可用（hello + 版本）
  ├─ 若不可用：
  │    open -n dist/native/AppleConnector.app --args --socket <state>/helper.sock
  │      └─ AppleConnector.app（bundle id com.jachy.apple-connector，自签名）
  │           └─ apple-connector-helper --socket ...（进程本身即 App，TCC 身份 = App）
  ├─ 等待 helper hello 成功
  └─ spawn node dist/src/transports/local/main.js
       └─ EventKitHelperClient 通过 Unix socket 发送 JSONL
```

关键点：

- App 的主可执行文件就是现有 `apple-connector-helper`，不新增第二个常驻进程。
- helper 不带参数运行时保持现有 stdin 模式；带 `--socket <path>` 时进入 socket 模式。
- App 的 `Info.plist` 提供固定 bundle id、显示名和 EventKit usage description；TCC 弹窗显示 “Apple Connector”。
- 自签名证书使 bundle 的 designated requirement 稳定为 `identifier + certificate leaf`，而不是 ad-hoc 的 `cdhash`。
- 测试/CI 使用 `APPLE_CONNECTOR_HELPER_MODE=direct`，由 CLI 直接启动 helper 的 socket 模式，不经过 LaunchServices；该模式仅用于开发和无 GUI 环境，TCC 仍归宿主。

## 具体改动

### 1. Native helper 增加 socket 模式

`native/Sources/AppleConnectorHelper/main.swift`：

- 解析 `--socket <path>`；无该参数时保持现有 stdin 循环，测试和直接调用完全兼容。
- 使用 POSIX `AF_UNIX` / `SOCK_STREAM`：`socket`、`bind`、`listen`、`accept`、`read`、`write`。
- 启动时创建父目录（`0700`），仅当旧路径是 socket 时 `unlink`；若是普通文件则报错退出，不删除用户文件。bind 后 `chmod 0600`。
- 每个连接按 JSONL 读取；单行上限仍为 1 MiB；复用现有 `respond` 逻辑。
  - 把 `respond(to:helper:decoder:encoder:)` 重构为返回 `String` 的 `handle(line:)`，stdin 与 socket 两种模式共用。
- 多连接按顺序处理（`accept` 一个、服务到 EOF、再接受下一个）；Node 客户端断线后重连。这样保持现有“单线程 EventKit”语义。
- 忽略 `SIGPIPE`；处理 `SIGTERM`/`SIGINT`：关闭监听、删除 socket 与 pid 文件、退出。
- 在 socket 同目录写 `helper.pid`（`0600`），fatal 错误追加到 `helper.log`，便于 `open` 吞掉 stdout 后排障。
- `hello` 的 `helperVersion` 改为读取 App bundle 的 `CFBundleShortVersionString`；独立运行时回退到当前版本。顺带修复现有硬编码 `0.16.1`。
- 不改变任何 action、payload、错误码或权限检查逻辑。

### 2. 组装并签名 App bundle

新增 `scripts/build-native.mjs`，替换现有 `build:native` 一行命令：

1. `swift build -c release --package-path native`。
2. 复制 helper 到 `dist/native/apple-connector-helper`（stdin 模式、native 测试和 direct 模式使用）。
3. 组装 `dist/native/AppleConnector.app/Contents/MacOS/apple-connector-helper`。
4. 生成 `Contents/Info.plist`：
   - `CFBundleIdentifier=com.jachy.apple-connector`
   - `CFBundleName=Apple Connector`、`CFBundleDisplayName=Apple Connector`
   - `CFBundleExecutable=apple-connector-helper`
   - `CFBundlePackageType=APPL`、`CFBundleShortVersionString` / `CFBundleVersion` 取 `package.json`
   - `LSMinimumSystemVersion=14.0`、`LSUIElement=true`
   - `NSCalendarsFullAccessUsageDescription`、`NSCalendarsUsageDescription`、`NSRemindersFullAccessUsageDescription`、`NSRemindersUsageDescription`
5. 用 `APPLE_CONNECTOR_SIGN_IDENTITY`（默认 `Apple Connector Local`）签名 App 与独立 helper；缺少证书时：
   - 默认失败并打印证书创建步骤；
   - 仅当 `APPLE_CONNECTOR_ALLOW_ADHOC=1` 时退回 ad-hoc，并打印醒目警告（CI/测试专用）。
6. 签名后执行 `codesign --verify --strict`，并输出 `Identifier`、签名身份和 designated requirement；要求 requirement 不含 `cdhash`。

`package.json`：

- `build:native` → `node scripts/build-native.mjs`。
- 拆分 `build:app`（web + TypeScript，不碰 native）与 `build`（`build:app` + `build:native`）。
- `start` 改为 `npm run build:app && node dist/src/cli/index.js start --foreground`，正常启动不再替换 helper。
- 新增 `signing:check`：检测默认/指定签名身份是否存在，不存在时打印证书创建步骤。

### 3. Node helper 客户端改为 socket 模式

`src/native/helper-client.ts`：

- 构造函数保持兼容：第一个参数仍是可选可执行文件路径；新增可选 `socketPath`。
- `socketPath` 存在时用 `net.connect({ path })` 连接，不 spawn 子进程；沿用现有 JSONL 分帧、pending 表、超时和错误映射。
- 连接阶段对 `ENOENT`/`ECONNREFUSED` 做短重试（启动竞态）；握手仍发 `hello` 并校验 `protocolVersion`。
- 连接关闭时以 `service_unavailable` 拒绝 pending；下一次调用自动重连。
- 未提供 `socketPath` 时保持现有 stdio 行为，native 测试无需改动。
- `close()` 在 socket 模式下只关闭连接，不杀 App。

`src/transports/local/main.ts`：

- 从 `APPLE_CONNECTOR_HELPER_SOCKET` 或 `statePaths().helperSocket` 构造客户端。
- 启动 warm-up 仍调用 `permissions.status`；失败只记录 service log，不影响管理服务启动（保持现状）。

### 4. 启动、停止与状态

`src/transports/local/paths.ts`：

- `StatePaths` 新增 `helperSocket`、`helperPidFile`、`helperLogFile`。
- 新增 helper 可执行文件/App 路径解析，集中管理 `dist/native` 相对路径。

`src/transports/local/lifecycle.ts`：

- `ensureHelperSocket(paths)`：
  - 若 socket 已能完成 `hello` 且 `helperVersion === appVersion`，复用。
  - 版本不一致、socket 无响应或 pid 失活时，先 `stopHelper()`，再启动新实例。
  - 默认：`open -n <AppleConnector.app> --args --socket <path>`；等待 socket + hello，超时给出 App 路径、`helper.log` 尾部和 Gatekeeper 提示。
  - `APPLE_CONNECTOR_HELPER_MODE=direct` 或非 darwin：`spawn(<helper>, ['--socket', path], { detached: true })`。
  - App 文件缺失时返回 `service_unavailable`，提示先运行 `npm run build` 或重新安装。
- `stopHelper(paths)`：按 `helper.pid` 发送 SIGTERM，等待 socket 消失；清掉残留 socket/pid。
- `startService()`：先 `ensureHelperSocket()`，再复用/替换 Node 服务；spawn Node 时注入 `APPLE_CONNECTOR_HELPER_SOCKET`。
- `startForegroundService()`：先 `ensureHelperSocket()`，设置环境变量后导入 `main.js`。
- `stopService()`：先停 Node，再停 helper；只有两者都未运行时才返回 `conflict`。等待两个 socket 都消失。
- `status()`：新增 `helper: { running, pid, socket }`（增量字段，不破坏旧输出）；CLI `status` 显示 helper 行。
- `openManagementWeb()` 与 `init` 复用 `startService`，行为不变。

`src/cli/index.ts` / `src/cli/ui.ts`：

- `status` 展示 helper 状态。
- `doctor --probe` 增加 helper 权限信息（socket 可用时读取 `permissions.status`），并明确 JXA probe 反映宿主进程、helper 状态才是 Apple Connector 的权威状态；避免升级后 `doctor` 仍显示宿主的 `calendar=0` 造成误判。

### 5. 权限迁移与页面提示

- 升级到 v0.17.0 后，App 是新的 TCC 身份：日历/提醒事项首次状态为 `not_determined`，需要在管理页第 1 步重新授权一次；旧宿主的授权不会被继承，也不会被删除。
- 管理页权限卡、`src/web/i18n.ts` 与 `src/web/docs.ts`（中英文）更新：
  - 明确系统设置中应出现 “Apple Connector”，而不是 Terminal/OpenCode；
  - `not_determined` 表示尚未对本 App 授权；`denied` 表示已在系统设置中关闭；
  - `permission_denied` 同时可能来自系统权限缺失或授权范围不足，排障顺序先系统权限、后授权范围；
  - 升级、切换签名身份后可能需要重新授权一次。

## 迁移与兼容性

- 现有 state dir、数据库、Agent 授权、审计记录、CLI 参数、RPC 方法全部不变。
- 升级后第一次启动会拉起 Apple Connector App；系统权限需要重新授权一次（旧宿主授权不继承）。
- 旧版本服务仍在运行时，`stop`/`start` 会停掉旧 Node 服务并切换到新 helper；不会自动删除用户数据。
- `start --foreground` 仍可用，但 helper 仍由 App 承载；前台进程只负责 Node 服务。
- `APPLE_CONNECTOR_HELPER_MODE=direct` 保留给测试、CI、无 GUI/SSH 排障；该模式权限归宿主，文档明确标注不要用于日常使用。
- 回滚到 v0.16.x 后，旧版本会重新以宿主权限运行，原宿主授权仍可用。

## 安全与风险

- App 只执行自身 bundle 内签名的 helper，不接受任意可执行文件或脚本路径参数；`--socket` 只接受绝对路径。避免把 TCC 授权变成任意代码执行入口。
- helper socket 位于 `0700` 的 state dir 内，socket 与 pid 文件 `0600`。信任模型与现有 `service.sock`/admin token 一致：同一用户进程可访问本机状态文件；跨用户不可访问。
- 私钥是核心资产：持有者可签出继承用户授权的 App。私钥只留在维护者本机/密码管理器，不进仓库、不进 CI、不打印。
- 证书轮换或改名等同于更换 TCC 身份，所有用户需重新授权一次；文档列出轮换流程。
- 自签名不等于公证：浏览器下载的 tarball 可能带 quarantine，首次 `open` 可能被 Gatekeeper 拦截；npm 安装路径通常不带 quarantine。文档给出“系统设置 → 仍要打开”和 `xattr` 排障方式，但不把公开 `.app` 分发纳入本次范围。
- LaunchServices 在无 GUI 会话（SSH）下可能无法弹窗；文档建议在本机 GUI 会话授权，或临时使用 direct 模式排障。
- 若前置验证发现自签名 App 被 Gatekeeper 阻止或 TCC 仍按路径归属，立即停止实现并回到方案评审，不静默退回旧架构。

## 前置验证（实现第一步，任一失败即停）

在正式改造前先完成最小闭环：

1. 组装一个带 `--socket` 模式的最小 App，用自签名证书签名，`open` 启动成功，socket 能完成 `hello`。
2. 管理页请求日历，系统弹窗显示 Apple Connector；允许后 helper `permissions.status` 为 `full_access`。
3. 用同一证书重建 App（cdhash 变化），重启后状态仍为 `full_access`。
4. 将 App 复制到另一路径启动，状态仍为 `full_access`。

只有 1–4 全部通过，才继续实现文档、测试、发布校验和版本收尾。

## 验收标准

1. `npm run build` 产出 `dist/native/AppleConnector.app`，`codesign --verify --strict` 通过；签名非 ad-hoc，identifier 为 `com.jachy.apple-connector`，requirement 含证书且不含 `cdhash`。
2. `apple-connector start` 启动 App 与 Node；`status` 同时显示两者；`stop` 停止两者并清理 socket/pid。
3. 管理页的权限状态来自 helper（App），系统设置中显示 Apple Connector；日历/提醒事项请求与拒绝路径均正常。
4. 重建、升级、复制路径后授权保持；ad-hoc 替换后授权丢失（用于验证机制，不作为发布方式）。
5. `npm test`、`npm run check:jxa`、`npm run release:verify`、`git diff --check` 通过；CI 在 ad-hoc + direct 模式下通过。
6. 文档覆盖证书创建、构建签名、首次授权、升级迁移、轮换、排障、安全边界和中英文入口。

## 追加需求（2026-11-19，已批准：全部展开）：第 3 步展示全部授权及其提示词

### 现状

- 第 3 步“复制提示词”只在本次会话刚创建授权时（`created` 状态）显示提示词。刷新页面、切换管理页签或重新打开管理页后，`created` 丢失，已有授权无法再复制提示词。
- 第 2 步的授权列表只显示名称、范围、绑定状态与删除操作，不提供提示词。

### 目标

1. 第 3 步始终列出全部未撤销授权；每个授权一张卡片，显示名称、绑定状态、过期时间、对应提示词和“复制提示词”按钮。
2. 本次会话刚创建的授权额外显示一次性授权码、含授权码的提示词及其复制按钮，并用“刚刚创建”标记区分。
3. 已存在授权只显示推荐版（不含授权码）提示词；授权码只在创建时返回一次，不落盘，不回显。
4. 第 3 步的完成状态改为“存在至少一个未撤销授权”，不再依赖本次会话的 `created`。

### 实现

1. `web/src/main.tsx`
   - 在 `activeStep === 3` 中用 `activeClients` 渲染提示词卡片。每个卡片的推荐提示词调用 `buildAgentPrompt({ language, token: '', credentialKey: client.id, includeToken: false })`。
   - `credentialKey` 就等于授权 ID：`src/transports/admin/main.ts` 创建授权时已经返回 `credentialKey: created.client.id`，因此不需要修改 RPC 契约。
   - 刚创建的卡片复用现有一次性授权码区块、含码提示词与复制按钮；其他卡片只显示推荐版与复制按钮。
   - 无未撤销授权时显示现有 `promptPlaceholder`。
   - 步骤 3 的 `state` / `tone` 与 stepper 改为基于 `activeClients.length > 0`。
   - 已撤销授权不进入第 3 步（提示词已不可用），仍保留在第 2 步供查看和删除。
2. `src/web/i18n.ts`（中英）：新增列表标题、列表说明、每张卡片的“刚刚创建”标记与复制成功文案；能复用的现有文案不重复新增。
3. `web/src/style.css`：新增提示词卡片/列表样式，沿用 `.agent-prompt` 的滚动高度。
4. 测试：`tests/agent-prompt.test.ts` 增加“仅凭已有授权 ID 也能生成推荐提示词且不含授权码”用例；`tests/web-i18n.test.ts` 断言新增中英文案存在。
5. 验证：`npx tsc -p tsconfig.json --noEmit`、`npm run build:web`、`node --test dist/tests/*.test.js`、`git diff --check`；手动在管理页确认刷新后仍能看到并复制每个已有授权的提示词。

### 非目标与兼容性

- 不修改数据库、RPC 方法、授权模型、CLI、审计或原生 helper。
- 不提供“重新显示授权码”的能力；含授权码提示词仅限刚创建时。
- 不改变第 2 步授权列表、第 4 步绑定逻辑和现有提示词内容。

### 待确认

- 建议已有授权只提供推荐版提示词，因为授权码无法恢复。若要求旧授权也能生成含码提示词，必须修改凭据存储与回显模型（跨层契约变更），需要单独批准。
