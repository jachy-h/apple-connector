## 已知风险与待验证项

- Calendar 已由管理端显式授予完整访问；新 helper 能唯一发现 `Agents`，但最终安装后的 TCC 归属仍待验证。
- 原有 osascript 授权不能视为新 helper 已授权；需验证 bundle、签名、安装位置和启动链路。
- Swift helper 新增已有本机冷/热及完整 RPC 证据；样本量仍不足以宣称跨环境 P95。
- EventKit 标识与 Apple Events 标识需显式适配，现有 Calendar 名称范围不能静默扩大。
- helper 与 SQLite 不构成原子事务；写入后失联仍可能结果未知，禁止自动重放。
- 默认 sandbox 不允许 Swift/clang 写入用户级编译缓存；在获准的本地构建环境中，Swift helper 已完成 release 编译。最终安装、签名和 TCC 归属仍待验证。

## 本轮验证

已通过 `npm run build`（包含 Swift release helper）和 TypeScript 回归。已完成无数据 `hello` 握手、权限状态读取和显式 Calendar 完整访问请求。`Agents` 日历被 EventKit 唯一定位，并在 2026-08-08 至 2027-09-07 的有界窗口查询中返回 0 项；未输出或持久化事件内容。修复了 helper 对带毫秒 ISO 时间的解析。

早期性能探针（专用 `Agents` Reminders 清单，UUID 标记对象已精确删除）曾记录 helper 内 `save` 17 ms、按 ID 回读核验 4 ms，但端到端 15,993 ms。后续分层测试证明这不是当前构建的稳定冷启动表现。

已开始 P0 A/B 实验：A 组使用当前常驻 Swift/EventKit helper，B 组只在存在固定、无交互且可核验的测试快捷指令时运行。实验会把冷/热调用、排队、容器解析、保存、核验和清理分开记录；任何超时写入都不会跨 provider 自动重试。

分层检查发现调试页仍连接到 2026-09-06 22:17 启动的旧 Node 服务进程；该进程空闲时没有常驻 Swift helper 子进程，因此页面已有的 22–63 秒 Reminders 新增记录不代表当前重构后的 EventKit 路径。服务随后已重启并加载新构建，再通过完整本地 RPC 链路复测。

重启加载新构建后，A 组结果如下；所有测试项均使用独立 UUID，并按返回的稳定 ID 精确删除且核验成功：

- 原始 Swift helper：冷创建 101.5 ms；热创建 37.5、36.4、43.2 ms。
- 热路径内部主要耗时：容器解析 19–22 ms、保存 8–9 ms、核验 8–13 ms。
- TypeScript `WebWrites` → helper → EventKit：冷创建 110.0 ms；热创建 53.0、43.3、38.0 ms。
- 完整本地 RPC 服务：首次调用 57.6 ms；后续调用 65.3、36.5、37.8 ms。

结论：调试页的 22–63 秒瓶颈是未重启的旧服务仍在执行旧写入路径，不是当前 EventKit 主方案。服务重启后完整链路已降到百毫秒以内。Shortcut B 组因用户确认主方案已经满足性能目标而停止，不再作为 provider 候选。

提交前验证已完成：`npm run check` 通过 66 项 TypeScript 测试并检查 21 个固定 JXA 脚本；首次全量检查发现生命周期 readiness 错误依赖 EventKit 诊断，修复后定向测试与全量检查均通过。`npm run release:verify` 已通过 v0.5.0 的生产构建、CLI 冒烟、运行依赖与 dry-run 包内容验证。
