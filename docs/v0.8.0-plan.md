# Apple Connector v0.8.0 计划：本地 stdio MCP 接入与产品分发

更新日期：2026-09-07
进度记录：[v0.8.0-progress.md](./v0.8.0-progress.md)

## 当前状态

已开始实现本地 stdio MCP 的日常使用闭环；签名安装包和发布渠道仍需独立的 Apple 开发者身份与干净机验收。

## 已确认的产品方向

1. 本机 nanobot 通过 **stdio MCP** 调用 Apple Connector，MCP 为 agent 的主要接入方式。
2. **始终保持本地性，后续也不考虑远程调用。** 不建设 HTTP/SSE MCP、远程设备连接、云端中继或托管数据服务。
3. 对外提供可直接安装的 macOS 本地连接器，附带 MCP 入口和辅助 CLI；用户安装后在自己的 Mac 上使用。
4. 业务能力、范围授权、幂等和操作状态统一由本地服务管理，客户端适配层保持轻量。

“仅本地”限定连接器的调用与服务边界，不承诺阻止 Apple 自身的 iCloud 同步，也不代表调用方 nanobot 的模型推理或后续数据处理必定在本机完成。

## 目标与现状

产品目标是让 agent 可靠使用用户授权范围内的 Apple 数据，并提供清晰的授权、可追踪的写入和稳定的安装升级体验。

当前已有后台服务、Unix domain socket、stdio MCP 薄入口、范围授权、变更计划及本地管理 Web。主要缺口为：

- MCP 日历能力仍以读取为主，管理 Web 已有的非重复日程写入尚未形成 agent 使用闭环。
- Reminders 创建的原生可靠性仍需收敛；v0.7.0 完整原生构建与回归尚有工具链阻塞。
- 用户仍需开发构建，没有无需安装 Node 或 Swift 工具链的正式安装包。
- 初次配对、配置生成和服务生命周期还未形成完整的日常使用体验。

Notes 延续 v0.7.0 的禁用状态，不纳入本版本恢复范围。

## 方案

### 1. 本地架构与进程职责

```text
nanobot ── stdio MCP 薄入口 ──┐
CLI / 脚本 ──────────────────┼── 本地连接器服务 ── 统一授权与操作状态 ── 原生组件 ── Apple 数据
本地管理界面 ────────────────┘
```

- 复用现有后台服务和 Unix domain socket。每个 MCP 客户端启动独立薄入口，共用本地服务及原生访问组件。
- MCP stdout 仅输出协议消息，日志使用 stderr 或本地日志文件。
- 完成首次授权后，日常调用无需用户手动启动服务或重复复制凭证；明确服务未运行、退出、恢复和版本不匹配时的行为。
- 后台组件在用户会话中运行；具体启动管理方式在实现前结合原生权限验证确定。
- 管理 Web 可继续通过 loopback 提供界面，保留已有会话、Host、Origin 和 CSRF 保护。这不是 HTTP MCP，也不提供远程访问。
- Mac 睡眠或原生数据不可用时返回明确状态，不通过远程服务绕过本地限制。

### 2. nanobot 接入与工具契约

- 使用 nanobot 已支持的 stdio MCP 配置，不开发承载业务逻辑的专属 Python 集成。
- 提供稳定的可执行入口、绝对路径配置生成和连接诊断，避免依赖开发目录或交互 shell 的 PATH。
- 配置包含工具范围及合理的调用超时；nanobot 的工具筛选只作为便利，服务端始终执行实际授权。
- 工具围绕明确业务操作设计：查询日历与日程、非重复日程创建/编辑/删除、查询提醒事项清单与事项、创建和完成提醒事项。具体工具名和参数在实现时统一确定，不把示意接口当作已发布契约。
- 写入能力逐项通过原生验证后才注册为可用；重复日程编辑不在本版本范围内。
- 自动授权的操作尽量一次调用完成，内部复用不可变计划及提交机制。
- 需要人工审批时返回待审批状态和操作 ID，由本地管理界面处理，再查询结果；不长期阻塞 MCP 调用等待用户。
- 明确时区、全天日期、目标容器、分页和结果边界；用稳定 ID 定位对象，避免仅凭名称误选同名容器。
- 能力声明与实际可用工具保持一致；旧工具的保留、替换及配置迁移需明确说明。

### 3. 写入可靠性、权限和辅助入口

- 所有写入携带稳定的客户端请求 ID；同一客户端重复请求返回原操作状态，相同 ID 配不同内容应被拒绝。
- 幂等记录在原生变更前持久化，并覆盖连接中断、客户端重试和服务重启。客户端不得在一次重试中自动换用新 ID。
- 本机 nanobot 的 MCP 实现存在连接错误重试逻辑，因此必须验证“原生写入成功但响应丢失”的场景。
- 结果未知时保留可查询状态，不自动重新执行变更，也不对用户宣称成功；优先查询和核对原操作。
- 原生写后验证、范围授权及审计由服务层执行，MCP、业务 CLI 和管理入口共享业务实现，各自保留明确的凭证权限边界。
- CLI 提供 JSON 业务输出及诊断、管理能力；业务调用不能隐式使用管理员凭证绕过客户端授权。管理操作不暴露为 agent 工具。
- 可选 Skill 仅补充日期歧义、默认清单和状态查询等使用约定，不承担授权或防重复执行保证。
- 保留凭证撤销、轮换、授权变更生效及审计脱敏机制；不宣称能隔离独立控制同一 macOS 账户的 agent。

### 4. 配对与管理体验

首次使用流程：打开连接器 → 明确申请系统权限 → 添加 agent → 选择允许的日历、清单和操作 → 生成 stdio MCP 配置 → 验证连接。

- 管理界面主要负责连接状态、原生权限状态、客户端授权、审批、审计和诊断。
- 保留现有 Web 实现和有用的 CRUD 验证界面，但不把产品扩展成完整日历或提醒事项客户端。
- 普通用户无需处理管理员 token。客户端凭证的持久化、读取及轮换方式在实现时确定，避免把秘密放入命令行参数或日志。
- 配置助手先展示将写入的配置差异，保留用户已有配置；本次计划记录不实际修改 nanobot 配置。

### 5. macOS 安装包与发布渠道

- 主交付物为轻量 macOS App，包含本地服务、原生访问组件、管理入口和 CLI/MCP 桥接程序。
- 复用现有 TypeScript 服务与 Web UI，可随产品携带运行时；不以全量 Swift 重写作为发布前提。
- 正式包不得要求用户自行安装 Node、Swift 工具链或现场编译。
- 稳定 App、helper 的安装位置和签名身份，明确哪个进程持有和请求原生权限；通过实际安装包验证，不能假定增加 App 外壳就解决授权问题。
- 正式分发使用 Developer ID 签名并完成 notarization，验证下载、首次打开、升级及原生权限体验。
- GitHub Releases 提供 DMG/ZIP；自有 Homebrew tap/cask 提供安装升级入口，并链接同一 App 内的 CLI。源码继续供开发者构建和贡献。
- npm 不作为完整原生产品的主要安装渠道；客户端插件只在有需要时提供配置与说明包装。
- 发布前明确支持的 macOS 最低版本和 CPU 架构；安装包、文档和实际验证结果必须一致。
- 升级应保持授权、客户端配置和操作记录兼容；卸载停止后台组件，用户数据清理必须明确区分普通卸载与主动删除。

## 实施顺序与阶段门槛

1. 恢复兼容的原生构建环境，补齐 v0.7.0 原生回归，确认日历与 Reminders 的可靠基线。
2. 统一业务操作和状态契约，补齐原生能力、授权校验、幂等与写后验证。
3. 完成本机 stdio MCP、辅助业务 CLI、服务生命周期及 nanobot 配对闭环。当前实现由 `mcp config --token-file` 生成绝对 Node/CLI 路径配置；凭证在 0600 常规文件中保存，stdio 入口自动启动或复用同版本本地服务，RPC 写入等待上限为 60 秒。
4. 收敛管理界面，形成权限、客户端连接、审批和诊断体验。
5. 制作包含运行时的 macOS App，验证权限承载进程、安装和升级。
6. 完成签名、公证、GitHub Releases 产物及自有 Homebrew cask，达到公开分发门槛后再发布。

先完成本机可用性，再进入分发阶段。证书、签名身份或验证机器不可用时应记录分发阻塞，不以源码构建成功替代正式安装包验收。具体签名身份、发布仓库和渠道配置在实施阶段核对，本计划不填入未经确认的值。

## 验收标准

1. nanobot 通过 stdio MCP 使用授权范围内的日历和提醒事项，无需专属业务集成；首次配对后可恢复日常使用。
2. agent 查询及通过验证的写入形成闭环，未授权容器和操作被拒绝；CLI 业务入口不能绕过同样的权限约束。
3. 自动授权写入一次业务调用可完成；人工审批返回可查询状态，审批后执行不可替换的原计划。
4. 重复请求、响应丢失、连接重建和服务重启不会造成同一操作重复写入；结果未知不会自动重做。
5. MCP 协议输出不混入日志；服务不可用、权限拒绝、能力不支持和操作失败均有稳定可理解的错误。
6. 连接器不提供 HTTP/SSE MCP、局域网或公网接入，管理网页仅限 loopback；不新增远程调用路径。
7. 正式安装包可在声明支持的干净 Mac 环境安装使用，无需 Node/Swift 开发环境；首次授权和升级后的原生访问通过验证。
8. 签名、公证、产物完整性、CLI 链接及升级兼容性通过检查，发布说明准确列出能力和限制。
9. Notes 保持禁用；真实 Apple 写入验收仅在明确选择的专用测试容器执行。

## 验证安排

- 契约与集成：工具 schema、授权、凭证撤销、幂等冲突、审批状态及新旧入口兼容。
- 故障场景：原生写入后响应丢失、nanobot 重试、服务重启、权限撤销及原生结果未知。
- 本机端到端：从配对到 nanobot 查询/写入/查询状态，验证超时和恢复行为。
- 安装分发：干净环境安装、系统授权、服务重启、升级、卸载及签名公证检查。
- 执行与变更相匹配的自动检查和原生回归，并持续记录进度与证据。

自动测试覆盖配置和凭证文件安全性、MCP 工具契约、幂等写入及本地服务授权边界。真实 Apple 写入、签名、公证和干净机安装仍按上述限制另行验证。
